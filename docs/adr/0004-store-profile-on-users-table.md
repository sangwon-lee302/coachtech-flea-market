# 0004 プロフィールを users テーブルに保存する

- ステータス: 採用
- 日付: 2026-10-10

## 背景

プロフィール設定画面（#29）で保存するプロフィール画像・ユーザー名・郵便番号・住所・建物名を、データベースのどこに置くかを決める必要がある。

- ユーザー名は会員登録で入力され、`users.name` に保存されている。ユーザーを識別するのはメールアドレスで、ユーザー名は画面に表示する名前である。
- プロフィール設定画面は、5 つの項目を 1 つのフォームでまとめて保存する。郵便番号と住所は入力を必須とし、建物名とプロフィール画像は任意とする。
- プロフィールの設定は強制しない。メール認証の後にプロフィール設定画面へ誘導するが（#31）、設定せずにほかの画面へ進める。そのため、住所を設定していないユーザーが、期間の定めなく存在する。住所がないことは、購入の時点で扱う。
- ユーザー名とプロフィール画像は、マイページ（#30）のほか、商品のコメントでも投稿者の表示として並べて使う見込みである。住所を読むのは、プロフィール設定画面と、届け先の初期値として使う商品購入画面だけである。
- 注文は、ユーザーの住所を参照するのではなく、届け先を自分の列に写して持つことになる。参照にすると、ユーザーが後で住所を変えたときに、過去の注文の届け先まで変わってしまうためである。
- プロフィール画像はファイルとして保存し、データベースにはその相対パスだけを持つ。

この ADR は、ユーザーの郵便番号と住所を書き込む画面がプロフィール設定画面だけであることを前提にしている。商品購入の機能（マイルストーン「M6 購入」）には送付先住所変更画面があり、そこで入力された住所をどこに保存するかはまだ決めていないが、ユーザーの住所を書き換えることはないものとした。

以下では、郵便番号と住所の片方だけが保存された状態を「不完全な住所」と呼ぶ。

## 決定

プロフィール画像のパス・郵便番号・住所・建物名を、`users` テーブルの NULL を許す列として持つ。ユーザー名は `users.name` のままにする。プロフィールや住所のためのテーブルは作らず、CHECK 制約も今は付けない。

## 検討した選択肢

### users テーブルの列にする

- 良い点:
    - フォームの 5 つの項目が 1 つのモデルに対応し、保存が 1 回の更新で済む。
    - ユーザー名とプロフィール画像を表示する画面で、リレーションを読み込む必要がない。
    - テーブル・モデル・リレーション・ファクトリーが増えない。
- 悪い点:
    - 住所を設定していないユーザーがいるため、郵便番号と住所は NULL を許す列になり、不完全な住所をデータベースが拒めない。不完全な住所を防ぐのは、両方を必須にするフォームリクエストだけである。
    - 認証のたびに読み込む `users` の行に、認証に使わない列が 4 つ加わる。
    - 公開しない住所が、画面に表示するユーザー名・プロフィール画像と同じテーブルに入る。

### users テーブルの列にし、CHECK 制約を付ける

上の選択肢に、`(postal_code IS NULL) = (address IS NULL)` という CHECK 制約を加える。

- 良い点:
    - テーブルを分けずに、不完全な住所をデータベースが拒む。
    - 保存・表示・部品の数についての良い点は、上の選択肢と変わらない。
- 悪い点:
    - Laravel のスキーマビルダーには CHECK 制約を書く手段がないため、マイグレーションに MySQL の SQL を直接書くことになる。テストも開発と同じ MySQL で実行しているので、テストだけが動かなくなることはない。
    - 認証に使わない列が加わることと、住所が表示用の項目と同じテーブルに入ることは、上の選択肢と変わらない。

### profiles テーブルに分け、初回の保存時に行を作る

ユーザー名は `users` に残し、プロフィール画像・郵便番号・住所・建物名を `profiles` に置く。

- 良い点:
    - 行を作るのが保存の時なので、郵便番号と住所を NOT NULL にでき、不完全な住所をデータベースが拒む。住所がないことは、行がないことで表される。
    - `users` に列が加わらない。
- 悪い点:
    - フォームの保存が 2 つのモデルへの書き込みになり、トランザクションが必要になる。
    - ユーザー名とプロフィール画像を表示する画面のすべてで、リレーションを読み込む必要がある。
    - テーブル・モデル・リレーション・ファクトリーが 1 つずつ増える。
    - NOT NULL の制約が、住所とは関係のないプロフィール画像と同じ行にかかる。行があることが「住所がある」ことを意味するため、住所を持たずに画像だけを持つ状態を表せない。
    - 公開しない住所が、画面に表示するプロフィール画像と同じテーブルに入る。

### profiles テーブルに分け、会員登録時に行を作ってユーザー名も置く

ユーザー名は識別には使わない表示用の名前なので、`users` から `profiles` に移す。プロフィール画像・郵便番号・住所・建物名も `profiles` に置く。

- 良い点:
    - フォームの 5 つの項目が 1 つのモデルに対応し、保存が 1 回の更新で済む。
    - `users` が認証に使う列だけになる。
- 悪い点:
    - ユーザー名は会員登録で入力されるため、行を会員登録の時点で作ることになる。その時点では住所がないので、郵便番号と住所は NULL を許す列になり、不完全な住所をデータベースが拒めない。
    - 会員登録が 2 つのモデルへの書き込みになり、トランザクションが必要になる。
    - ユーザー名を表示する画面のすべてで、リレーションを読み込む必要がある。
    - テーブル・モデル・リレーション・ファクトリーが 1 つずつ増え、ユーザーを作るテストのすべてでプロフィールも作る必要がある。
    - 公開しない住所が、画面に表示するユーザー名・プロフィール画像と同じテーブルに入る。

### 住所だけを addresses テーブルに分ける

ユーザー名とプロフィール画像は `users` に置き、郵便番号・住所・建物名を `addresses` に置いて、初回の保存時に行を作る。

- 良い点:
    - 行を作るのが保存の時なので、郵便番号と住所を NOT NULL にでき、不完全な住所をデータベースが拒む。住所がないことは、行がないことで表される。制約がかかるのは住所だけで、プロフィール画像を巻き込まない。
    - ユーザー名とプロフィール画像を表示する画面で、リレーションを読み込む必要がない。
    - 公開しない住所が、画面に表示するユーザー名・プロフィール画像とは別のテーブルに入る。
    - `users` に加わる列が、プロフィール画像のパスだけになる。
- 悪い点:
    - フォームの保存が 2 つのモデルへの書き込みになり、トランザクションが必要になる。
    - テーブル・モデル・リレーション・ファクトリーが 1 つずつ増える。

## 理由

テーブルを分けて得られるものは、このアプリでは、不完全な住所をデータベースが拒むことだけである。その不完全な住所は、今のアプリでは起こりえず、仮に起こったとしても害は小さく、データベースで拒みたくなれば `users` の列のままでも拒める。一方、分ければ保存の処理と保守する部品が増える。そのため、`users` の列にする。

テーブルを分ける選択肢にあって、`users` の列にする選択肢にない良い点は、不完全な住所を拒めること、`users` に認証に使わない列をほとんど加えずに済むこと、公開しない住所を表示用の項目と別のテーブルに置けることの 3 つである。後の 2 つは、このアプリでは差にならない。`users` に加わるのは短い列が 4 つで、認証のたびに読み込む行の大きさはほとんど変わらない。同じテーブルにあることで住所が意図せず表に出るとすれば、`User` モデルを JSON にして返す場合である。これは、`User` モデルの `Hidden` 属性に郵便番号・住所・建物名を加えれば防げ、テーブルを分ける必要はない。残るのは、不完全な住所を拒めることである。

不完全な住所は、今のアプリでは起こりえない。ユーザーの郵便番号と住所を書き込むのはプロフィール設定画面だけで、そのフォームリクエストが両方を必須にしているためである。

仮に起こったとしても、害は小さい。住所を読むのは、プロフィール設定画面と商品購入画面だけである。プロフィール設定画面は、保存されている値をフォームの初期値にするだけなので、ユーザーが欠けた項目を入力して保存すれば直る。商品購入画面は、プロフィールの設定を強制していないため、住所を設定していないユーザーをもともと扱う必要があり、不完全な住所を持つユーザーもそれと同じように扱えばよい。郵便番号と住所が必ずそろっていなければならないのは、注文の届け先である。届け先は注文が自分の列に持つので、その列を NOT NULL にすれば、仮に商品購入画面が不完全な住所を見落としたとしても、それがそのまま注文に使われることはない。

それでも不完全な住所をデータベースで拒みたくなれば、テーブルを分けなくても、`users` に CHECK 制約を付ければ拒める。したがって、分ける選択肢でしか得られない良い点は残らない。その制約を今は付けないのは、不完全な住所を作りうる経路が今のアプリにないためである。付ければ、スキーマビルダーで書けない SQL をマイグレーションに持つことになるが、それで防げるものが今はない。

防ぐものができるとすれば、送付先住所変更画面がユーザーの住所を書き換えることになるなどして前提が崩れた場合である。その場合も、この決定は変わらない。その画面のフォームリクエストも郵便番号と住所の両方を必須にすれば、不完全な住所はやはり起こりえない。ただ、同じ規則を 2 つのフォームリクエストが別々に持つことになり、いつか片方だけが変わるおそれが生まれる。CHECK 制約を付けるかは、その画面の保存先を決める時に判断する。その時までは不完全な住所の行ができないので、既存の行が制約を付ける妨げになることもない。

CHECK 制約は後に回すが、`Hidden` 属性は今から設定する。扱いを分けるのは、必要になった時に気付けるかどうかと、気付けなかったときの害の大きさが違うためである。書き込む経路が増えるのは送付先住所変更画面の保存先を決める時で、そこで判断できる。一方、`User` を JSON にして返す処理は、今はないが、コメントを投稿者とともに返すといった形で、住所のことを考えないまま加わりうる。そのとき漏れるのは個人の住所であり、入力し直せば済む不完全な住所に比べて害は一段大きい。

テーブルを分ける費用の方は、今から発生する。費用が最も小さい `addresses` でも、1 つのフォームを 2 つのモデルにトランザクションで保存し、テーブル・モデル・リレーション・ファクトリーを 1 つずつ保守することになる。それで得られるのは、CHECK 制約 1 つで得られるものと同じである。`profiles` に分ける 2 つの選択肢は、`addresses` よりも劣る。初回の保存時に行を作る場合は、`addresses` の費用に、ユーザー名とプロフィール画像を表示する画面でのリレーションの読み込みが加わる。会員登録時に行を作る場合は、その時点で住所がないために不完全な住所を拒めず、テーブルを分けて得られる唯一の良い点すらない。

1 人が複数の住所を持つ機能が必要になれば、住所のテーブルが要る。しかし、これは今分ける理由にならない。その機能が必要になるかは分からず、必要になった時に `users` の列から移すのは難しくない。テーブルを作り、郵便番号と住所のある行を写し、列を落とすマイグレーション 1 つで済み、1 人に住所が 1 つなので、写すときに迷うこともない。今 `addresses` に分けておいても、1 人に 1 行の作りなので、どの住所を届け先の初期値にするかを決める仕組みを後から加えることになり、そのまま使えるわけでもない。

## 結果

- `users` テーブルに、プロフィール画像のパス・郵便番号・住所・建物名の列を、すべて NULL を許す列として追加する。
- 郵便番号・住所・建物名を、`User` モデルの `Hidden` 属性に加える。`User` を JSON にして返す処理が加わっても、誤って住所が含まれないようにするためである。
- 「住所が設定されている」とは、郵便番号と住所がどちらも NULL でないことを指す。商品購入画面はこの定義で判定し、不完全な住所を、住所を設定していない場合と同じように扱う。
- 不完全な住所を防ぐのは、プロフィール設定画面のフォームリクエストである。送付先住所変更画面が `users` の列に保存することにする場合は、その時に CHECK 制約を付けるかを決める。郵便番号と住所を書き込む経路がほかに増える場合も同じである。
- 注文のテーブルを作るとき、届け先の郵便番号と住所は注文自身の列として持ち、NOT NULL にする。この制約は最後の歯止めであり、商品購入の処理は、支払いを始める前に届け先がそろっていることを検証する。
- 1 人が複数の住所を持つ機能が必要になったときは、住所を `addresses` テーブルに移す。
