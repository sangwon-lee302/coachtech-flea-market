# 0001 スタイルに Tailwind CSS を使う

- ステータス: 採用
- 日付: 2026-09-26

## 背景

画面のスタイルをどう書くかを決める必要がある。Laravel のスケルトンには、Tailwind CSS を使うための設定が最初から入っている。

- `package.json` に、`tailwindcss` と、Vite のビルドで Tailwind CSS を動かす `@tailwindcss/vite` が入っている。
- `vite.config.js` で `@tailwindcss/vite` のプラグインが有効になっており、`resources/css/app.css` がビルドの入り口になっている。
- `resources/css/app.css` が `@import 'tailwindcss'` で Tailwind CSS を読み込んでいる。
- Laravel のページネーションのビューは、既定で Tailwind CSS のクラスを使う。

Tailwind CSS v4 は、プロジェクト内のファイル（`.gitignore` で除外したものを除く）から使われているクラスを自動で探し、必要な CSS だけを生成する。そのため、Blade ファイルの場所を設定する必要がない。`app.css` の `@source` は、自動では探さない `vendor/` 内のページネーションのビューなどを追加で指定している。

## 決定

Tailwind CSS を使う。

## 検討した選択肢

### Vanilla CSS

- 良い点: 依存するパッケージがなく、CSS の機能をそのまま使える。
- 悪い点: クラス名の付け方を自分で決め、マークアップとは別にスタイルシートを管理し続ける必要がある。画面が増えるほど、どのルールがどこで使われているかを追いにくくなり、使われなくなったルールが残りやすい。

### Bootstrap（コンポーネント型）

- 良い点:
    - ボタン、フォーム、ナビゲーション、モーダルなどの部品がそろっており、既定の見た目のままでよければ速く画面を作れる。
    - `btn btn-primary` のように、少ないクラスで部品を表せる。
    - モーダルやドロップダウンなど、動きのある部品の JavaScript も含まれる。
- 悪い点:
    - このアプリには、黒いヘッダーや赤いボタンといった独自のデザインがある。既定の見た目から離れるほど上書きの CSS を書くことになり、速く作れる利点が薄れる。
    - 使わない部品の CSS も配信される。必要な部品だけに絞るには、Sass で読み込む部品を自分で選ぶ必要がある。
    - Laravel で使うには、次の作業が必要になる。一度きりの小さな作業ではある。
        - `bootstrap` と、ドロップダウンなどが依存する `@popperjs/core` をインストールする。
        - Bootstrap の CSS と JavaScript を `app.css` と `app.js` で読み込む。色などを変数で変えるなら、`sass` も入れて入り口を Sass のファイルにする。
        - Tailwind CSS のパッケージ、Vite のプラグイン、`app.css` の記述を取り除く。
        - `AppServiceProvider` の `boot()` で `Paginator::useBootstrapFive()` を呼び、ページネーションのビューを Bootstrap 用に切り替える。

### Tailwind CSS（ユーティリティ型）

- 良い点:
    - ユーティリティがおおむね CSS のプロパティ 1 つに対応するため、決まった見た目に縛られず、独自のデザインをそのまま表せる。CSS の知識もそのまま生きる。
    - 使われているクラスの CSS だけを生成するため、配信する CSS が小さく済む。
    - スケルトンの設定のまま使える。
    - 広く使われており、実務で求められる機会が多い。身につけた技術を実務に生かせることも、このプロジェクトでは選ぶ理由になる。
- 悪い点:
    - ユーティリティを並べるためクラスの列が長くなり、マークアップが読みにくくなりやすい。
    - 動きのある部品は含まれず、必要なら JavaScript を自分で書く。

## 理由

Vanilla CSS では、クラス名とスタイルシートの管理をすべて抱えることになる。フレームワークを使えばその多くを省けるため、フレームワークを使う。

Bootstrap の速さと短いクラスの列は、既定の見た目を使う場合の利点である。独自のデザインを持つこのアプリでは、その速さが上書きの手間に変わる。

Tailwind CSS の悪い点のうち、クラスの列の長さは、繰り返し使う部分を Blade コンポーネントにまとめれば抑えられる。そうすると、Bootstrap の短いクラスの列という利点もほとんど残らない。動きのある部品はこのアプリでは少なく、いいねボタンのように独自に書く部分は、どちらを選んでも変わらない。

## 結果

- スタイルは Blade のクラス属性に書き、繰り返し使う部分は Blade コンポーネントにまとめる。
- 動きのある部品が必要になったときは、JavaScript を自分で書く。
- 画面を表示するには Vite でアセットをビルドする必要がある。テストではビルドせずに実行できるよう、Vite を無効にする。
