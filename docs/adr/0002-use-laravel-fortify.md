# 0002 認証に Laravel Fortify を使う

- ステータス: 採用
- 日付: 2026-09-28

## 背景

会員登録・ログイン・ログアウトをどう実装するかを決める必要がある。このアプリが認証に求めるのは次の機能だけで、2 要素認証やパスワードの再設定は必要としない。

- ユーザー名・メールアドレス・パスワード・確認用パスワードによる会員登録
- メールアドレスとパスワードによるログイン
- ログアウト
- メールアドレスの認証（#19 で実装する）

画面は Blade と Tailwind CSS で作っている（ADR 0001）。

認証は、ほかの機能と違い、誤りが目に見える不具合として現れにくい。ログインの前後でセッションを再生成し忘れる、ログインの試行回数を制限し忘れるといった誤りがあっても、画面は正しく動く。テストで防げるのは、テストを書く側が知っている脅威だけである。

## 決定

Laravel Fortify を使う。Fortify に手を加えるのは、ビュー・ログイン後の遷移先・有効にする機能・パスワードの規則・ログインの試行回数の制限のように、Fortify が変更する場所として用意しているところだけにする。

## 検討した選択肢

### Laravel の機能で自作する

- 良い点:
    - 入力の検証をほかのフォームと同じくフォームリクエストで書け、内容も自由に変えられる。
    - 追加で依存するパッケージがなく、使わない機能も入らない。
- 悪い点:
    - パスワードのハッシュ化・CSRF 対策・セッションの管理・署名付き URL といった部品は Laravel が提供するが、それらを正しい場面で正しく呼ぶ部分は自分で書き、保守することになる。この部分の誤りは画面にもテストにも現れにくく、正しいことを確かめるには認証の知識が要る。
    - メールアドレスの認証も自分で実装する。Laravel が必要な部品を提供しているため、量は少ない。

### スターターキット

- 良い点: 認証の機能と画面が最初からそろっている。
- 悪い点:
    - スターターキットは、`laravel new` でアプリを新しく作るときに選ぶ雛形である。既存のアプリには追加できないため、リポジトリを作り直すことになる。
    - Livewire と Flux UI、または React・Vue・Svelte のいずれかが加わり、Blade で作った画面と構成が変わる。
    - ダッシュボードや設定の画面など、このアプリにない画面が含まれ、独自のデザインに合わせて取り除くか書き換えることになる。
    - 認証の処理には Fortify を使っているため、入力の検証がフォームリクエストと揃わない点は Fortify と変わらない。

### Laravel Breeze

- 良い点:
    - Blade で画面を作る構成があり、このアプリの構成と一致する。
    - ログインの入力の検証にフォームリクエストを使う。
- 悪い点:
    - 認証のコードをアプリに書き出す方式のため、書き出した後のコードは自分で保守することになる。Laravel 12 で公式のスターターキットから外れ、更新も止まっているため、書き出す元のコードも直されない。
    - 会員登録の入力はコントローラーの中で検証しており、フォームリクエストと揃うのはログインだけである。
    - 独自のデザインの画面や、プロフィールとダッシュボードの画面が含まれ、取り除くか書き換えることになる。

### Laravel Fortify

- 良い点:
    - 画面を持たず、ルートと認証の処理だけを提供するため、Blade で作った画面をそのまま使える。
    - 認証の処理はパッケージとして保守されており、修正は `composer update` で取り込める。
    - 有効にする機能を選べ、会員登録とメールアドレスの認証がちょうど含まれる。
    - 現在のスターターキットも認証に Fortify を使っており、身につけた使い方がほかの Laravel のアプリにも生きる。このプロジェクトでは、これも選ぶ理由になる。
- 悪い点:
    - 処理が `vendor/` の中にあり、振る舞いを変えるには Fortify のアクションやレスポンスの契約を理解する必要がある。
    - 会員登録の入力は `CreateNewUser` アクションで、ログインの入力は Fortify の `LoginRequest` で検証する。ほかのフォームで使うフォームリクエストとは書き方が揃わない。
    - 使わない 2 要素認証とパスキーのためのパッケージも依存関係として入る。
    - 無効にしている機能のルートの一部（`user/confirm-password`）も登録される。

## 理由

課題の仕様は認証に Fortify を使うよう指定しており、このプロジェクトはそれに従う必要がある。そのため Fortify を使う見込みは高いが、指定をそのまま受け入れるのではなく、使える選択肢を自分で調べて比べた。アーキテクチャに関わる決定を自分で経験するためと、比べた結果、必要だと考えれば仕様に改善を提案するためである。こうした決定の経験は、学びと成長のうえで価値がある。これはこのプロジェクトに固有の理由である。

比べた結果、仕様の指定がなくても Fortify を選ぶ。決め手は、自分の認証の知識では、自作した認証のコードが実用に耐えるかを自分で確かめられないことである。背景に書いたとおり、認証の誤りは画面にもテストにも現れにくく、見落としに気付くには知識が要る。認証については、このプロジェクトの一部として片手間に学ぶのではなく、このプロジェクトに限らずもう少し時間をかけて学ぶことにし、ここでは自作しない。これも自分の現在の知識に基づく、このプロジェクトに固有の理由である。

自作の利点のうち、入力の検証をフォームリクエストで揃えられることは、Fortify を使えば失う。一方、依存するパッケージが増えないことの差は小さい。使わないパッケージは実行時には何もせず、更新の対象が増えるだけである。画面の構成が合うかどうかは、画面を持たない Fortify とも差がない。

スターターキットは、リポジトリを作り直し、画面の構成を変え、不要な画面を取り除く手間に見合わない。認証の処理は Fortify なので、入力の検証が揃わない点も解決しない。Breeze は画面の構成が合うが、書き出したコードを自分で保守することになり、自作と同じく、確かめられないコードを抱えることになる。残る Fortify が、リポジトリを作り直さず、書き出したコードも抱えずに、パッケージの保守と修正を受けられる選択肢である。

Fortify で入力の検証が揃わない点は、揃えずに受け入れる。揃えるには、ログインではサービスコンテナで Fortify の `LoginRequest` を自分のフォームリクエストに差し替え、会員登録では、Fortify のコントローラーがフォームリクエストを受け取らないため、規則をトレイトにまとめて `CreateNewUser` から使うことになる。仕様は当初、会員登録とログインの入力もフォームリクエストで検証するよう求めていたが、Fortify の仕組みに合わないことを伝え、仕様が改められた。揃わないのは会員登録とログインの 2 つのフォームだけで、以降のフォームはすべてフォームリクエストで書くため、影響はもともと限られる。無理に揃えれば保守するコードが増え、揃わないことの重みはそれに見合うほど大きくない。

以上から、Fortify を使うという仕様の指定には、改善を提案せずに従う。一方、会員登録とログインの入力の検証についての指定は、前段のとおり改善を提案し、仕様が改められた。

## 結果

- 会員登録の入力は `CreateNewUser` で、ログインの入力は Fortify の `LoginRequest` で検証する。ほかのフォームの入力はフォームリクエストで検証する。
- 使わない機能のためのパッケージと、`user/confirm-password` のルートは残る。
- Fortify が変更する場所として用意していない振る舞いが必要になったときは、この決定を見直す。
