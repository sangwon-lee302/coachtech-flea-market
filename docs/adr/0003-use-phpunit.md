# 0003 テストに PHPUnit を使う

- ステータス: 採用
- 日付: 2026-09-28

## 背景

テストをどのフレームワークで書くかを決める必要がある。

- Laravel のスケルトンには、PHPUnit で動くテストの設定（`phpunit.xml` と `tests/TestCase.php`）が最初から入っている。これまでに書いたテストも PHPUnit で書いており、CI は `sail test` でテストを実行している。
- Larastan は `tests/` も最も厳しいレベル（max）で解析しており、テストのコードにもアプリのコードと同じ型の厳しさを求めている。
- このアプリのテストは数が多くなり、そのうち多くは、項目ごとのバリデーションのメッセージのように、入力だけが違う同じ形のテストになる。
- ログインした状態を作る `actingAs()`、セッションのエラーを確かめる `assertSessionHasErrors()`、`RefreshDatabase`、ファクトリーといった Laravel のテストの機能は、どのフレームワークで実行しても同じように使える。

## 決定

PHPUnit を使う。

## 検討した選択肢

### PHPUnit

- 良い点:
    - スケルトンの設定のまま使え、変更するものがない。
    - テストは `TestCase` を継承したクラスなので、追加のパッケージなしで Larastan が型を理解できる。
    - 使わない機能のためのパッケージが入らない。
    - 歴史が長く、既存のプロジェクトの多くが PHPUnit で書かれていると考えられる。これは調べた結果ではなく推測である。そうしたプロジェクトのテストを読み、保守できることは実務で求められる。身につけた技術を実務に生かせることも、このプロジェクトでは選ぶ理由になる。
- 悪い点:
    - クラスとメソッド名を書く必要があり、テストが長くなる。入力だけが違うテストは、static メソッドのデータプロバイダーを用意し、`#[DataProvider]` 属性で指定する。
    - アーキテクチャテストやミューテーションテストには、PHPat や deptrac、Infection といった別のツールを導入する必要がある。

### Pest

- 良い点:
    - クロージャで書き、`expect()` をつなげて検証するため、テストが短くなる。入力だけが違うテストは、データセットで簡潔に書ける。
    - アーキテクチャテストとミューテーションテストの機能を備えている。
    - PHPUnit の上に作られており、PHPUnit のテストのクラスもそのまま実行できる。
- 悪い点:
    - Pest を導入する必要がある。これまでに PHPUnit で書いたテストはそのまま実行できるが、書き換えなければ 2 つの書き方が混在する。
    - Larastan にクロージャの中の `$this` の型を理解させるには、`pestphp/pest-plugin-phpstan` を導入し、`phpstan.neon` に読み込む設定を加える必要がある。このプロジェクトで試したところ、`$this` や `beforeEach()` で代入したプロパティの型は正しく推論されたが、データセットの値がテストの引数の型に合うかは検査されなかった。型を書いたデータプロバイダーより、検査が緩くなる。
    - 使わなくても、アーキテクチャテストとミューテーションテストの機能が入る。

## 理由

PHPUnit はすでに動いており、Pest は PHPUnit のテストのクラスをそのまま実行できる。そのため、後から Pest に移るときも、既存のテストを書き換えずに少しずつ移れる。Pest の機能が必要になる前に、Pest とそのプラグインを抱える理由はない。

Laravel のテストの機能はどちらでも同じなので、このアプリで Pest が優れるのは書き方、特に同じ形のテストをデータセットで簡潔に書けることである。PHPUnit を選ぶ代わりに、データプロバイダーを使う長い書き方を受け入れる。

静的解析は、当初は PHPUnit を選ぶ決め手になると考えていた。Pest のクロージャの中では、Larastan が `$this` の型を理解できず、最も厳しいレベルで解析するテストのコードでエラーになると考えたためである。しかし、Pest の公式のプラグインがこれを解決しており、このプロジェクトで試しても、`$this` を使うテストは正しく解析された。残る差は、プラグインを 1 つ導入することと、データセットの型が検査されないことだけで、決め手にはならない。

既存のプロジェクトのテストを読み、保守できるようになることも、このプロジェクトに固有の理由として PHPUnit を選ぶ側に加わる。

以上のとおり、Pest を技術的な理由で退けたのではない。今は移る理由がなく、移るとしても後から少しずつ移れるため、PHPUnit を使い続ける。

## 結果

- テストは `Tests\TestCase` を継承した PHPUnit のクラスとして書き、入力だけが違うテストは `#[DataProvider]` で書く。
- アーキテクチャテストやミューテーションテストが必要になったときは、PHPat・deptrac・Infection を導入するか、Pest に移るかを比べて決める。Pest に移る場合は、既存のテストを残したまま少しずつ移れる。
